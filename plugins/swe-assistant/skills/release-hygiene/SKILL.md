# release-hygiene

## Source

*The Missing Readme* (Riccomini & Ryaboy, No Starch Press 2021), **Chapter 8, "Delivering Software"** — the **Release** section. The ownership framing (*"don't throw releases over the fence"*), the immutability rule, the release-repository recommendation, the release-cadence guidance, and the changelog/release-notes split all come from here.

Automated changelog generation from commit messages / issue-tracker labels is widely-attested industry practice; the *Conventional Commits* spec (https://www.conventionalcommits.org) and tools like `git-cliff`, `standard-version`, `semantic-release`, and GitHub's autogenerated release notes are the operational instances. The commit-message discipline that makes it work is covered separately in [`commit-and-pr-hygiene`](../commit-and-pr-hygiene/SKILL.md).

## Pillars this skill strengthens

- **Primary:** Execution, Communication
- **Also:** Technical Knowledge (release repositories, versioning, publishing tooling)
- **Builds:** Leadership (owning the release end-to-end is one of the norms a senior engineer sets)

## What this skill is for

The build produces a package. The release is what makes that package **exist for users**: published to a repository, tagged with a version that will never change, accompanied by notes that tell people what's in it, on a cadence they can plan around. Get the release right and the deploy is a mechanical follow-through. Get it wrong and users find out you shipped a breaking change by hitting it in production.

This skill fires when the user is at any of the release decisions: how often to release, where to publish, how to write the notes, how to be transparent about the schedule, or how to keep the release ownership on the team that wrote the code. It does not fire once the release is out and the question shifts to how it gets rolled out to environments and users — that's `operator-playbook` territory (and eventually a dedicated rollout skill).

## The core mindset (lead with this)

**A release is a promise you can't take back. Own that promise end-to-end.**

- Once a version is published, it exists — for consumers, for lockfiles, for support tickets six months later. Rewriting it under the same version number is a lie about what's shipped where.
- "The release team will handle it" is how bugs reach users you didn't know existed. The engineer who wrote the code is the one who best understands what breaks; step out of the pipeline and that knowledge exits with you.
- Users won't read your commit history. If you didn't write release notes, you shipped a surprise.
- The right release cadence is *as often as you can afford to*. Small releases have small blast radii.

## How to run

Follow the [Output Protocol](../../../../docs/METHODOLOGY.md#10-output-protocol): **one question per turn, work on the user's actual release if shared, skip diagnosis if the first message tells you what they need.**

### Step 1 — Frame the moment

One or two sentences. Name that the release is when the built package becomes real for users, and that ownership matters here more than most engineers expect. Skip if the user already has a specific decision queued up.

### Step 2 — Diagnose (one question, only if needed)

The situation usually falls into one of these shapes:

- **Cutting a specific release now** — writing notes, tagging, publishing.
- **Designing or tightening the process** — where to publish, what to automate, who owns it.
- **Cadence question** — releasing weekly vs. on-commit vs. quarterly.
- **Fixing a problem** — a released version has a bug and someone wants to "just overwrite it," or the team is thrashing on releases nobody sees.

If the message is ambiguous, ask **one** question — for example: *"What's the situation — cutting a release now, designing the process, or reacting to something that just shipped?"*

### Step 3 — Ownership: don't throw releases over the fence

If the user's team hands releases off to a separate group and steps away, this is the first thing to fix.

- **Know how and when your code ends up in front of users.** Not roughly — specifically. Which repository? What triggers publication? Who gets paged if it fails?
- **Verify the release works in a test-like environment** before it reaches users. Even a smoke test that the package installs and the binary starts is more than most teams do.
- **Track the schedule.** If you don't know when your code ships, you don't own it.
- **If half your app ships or a critical bug reaches production, you're on the postmortem.** Nobody understands the code as well as the people who wrote it; nobody else can tell you what to fix so it doesn't happen again.

Ownership doesn't mean the release engineer is the person clicking publish — it means the engineering team is accountable for what got published and how it behaves.

### Step 4 — Publish to a release repository

Built packages belong in a **purpose-built package repository**, not in version control.

- **Release repositories** (Artifactory, Nexus, GitHub Packages, GitLab Package Registry, PyPI, npm registry, crates.io, Maven Central, ghcr.io, ECR, Docker Hub) are built for this: they serve artifacts, expose versioned APIs, integrate with deploy tooling, and act as an archive for debugging, rollback, and phased deployment.
- **Private repositories** are appropriate for internal-only software and for staging release candidates before public publication.
- **VCS is not built for this.** It can be forced into the role, but you lose search, retention policies, artifact metadata, and — most importantly — the isolation between "developer tools traffic" and "deployment traffic." A CI or deploy job hammering the repo can starve `git clone` on developers' machines.

Ask: *"Where do your built packages live today? Would a developer or an on-call engineer know how to find version 2.3.7 in an hour?"*

### Step 5 — Immutability

**Once published, a release package is never changed, never overwritten, never re-tagged.** Not ever.

- A version that can silently change is not a version. Lockfiles lie, deploys become non-reproducible, rollback becomes "roll to something that isn't there anymore."
- If you shipped a broken `1.4.2`, the fix is `1.4.3` (or `1.4.2+hotfix.1` if the ecosystem allows metadata suffixes). **Never** re-cut `1.4.2` under the same number.
- Some registries enforce this (Maven Central, crates.io). Some don't (Docker Hub tags, npm before 2016, homegrown Artifactory setups). If your registry lets you overwrite, tighten the config or wrap publishing in a script that refuses.

If they've *already* published a broken version and want to fix it: yank if the registry supports it (`npm deprecate`, `cargo yank`), publish the fixed version, communicate what happened in the release notes for the new version.

### Step 6 — Release cadence

The right cadence is as frequent as the team, the software, and the users can absorb.

- **Fewer changes per release = easier debugging.** When a bug reaches production, the shorter the list of changes since the last known-good release, the faster you find the culprit.
- **Continuous release** (release on every commit) is achievable when packaging, publication, and deploy are automated and users tolerate frequent changes — typical for internal services and SaaS backends.
- **Time-based cadences** (weekly, monthly) work for software where users need predictability — libraries, SDKs, customer-installed apps.
- **Feature-based cadences** ("release when X is done") work for large, milestone-shaped software but tend to grow the change set to a size no reviewer can fully hold in their head. Compensate with strong feature flags and CI.

The wrong answer is a cadence nobody understands. Whatever it is, name it, and publish it.

### Step 7 — Transparency about the schedule

Whatever the cadence, users need to be able to plan around it.

- **Publish the release schedule** somewhere users can find it (docs site, README, changelog header, release notes index).
- **Notify users when a release ships.** Mailing list, Slack channel, RSS on the changelog, GitHub Releases webhook — whichever channels your users actually watch.
- **Announce breaking changes ahead of time**, not on the day. A deprecation notice in `2.7.0` is how consumers get to `3.0.0` without setting a fire.

### Step 8 — Changelogs and release notes

Two different documents, two different audiences. Both required.

- **Changelog** — comprehensive, chronological, machine-generated when possible. Every ticket fixed, every commit that shipped. Audience: internal developers, support engineers, other maintainers debugging six months from now.
- **Release notes** — curated, human-written, summary-shaped. What's new, what's changed, what to watch out for. Audience: users.

The details are in the *Callout — Changelogs vs. release notes* below. If the team is already automating one and neglecting the other, work on the one they're neglecting.

### Step 9 — Pick one action, then close

Ask: *"What's one release-hygiene move you'll make this week?"* Push for concreteness.

- *"Improve our release process"* → too vague.
- *"Publish the release schedule at the top of our README by Friday, and set up an announcements channel"* → the action.

Close in one or two sentences. Confirm the move. If the next question is "how do I actually get this release onto our production servers," route to [`operator-playbook`](../operator-playbook/SKILL.md) for the delivery-pipeline framing and to the eventual deploy/rollout skills.

## Callout — Changelogs vs. release notes

Two documents, two audiences, both required. Teams that publish only one usually leave the users guessing (they published a changelog nobody reads) or leave support engineers grepping commit messages (they published release notes but no changelog).

### Changelog

- **Audience:** developers, support engineers, other maintainers.
- **Content:** every ticket fixed, every commit that shipped, in chronological order.
- **Level of detail:** exhaustive. If it was in the release, it's here.
- **Voice:** terse, factual, often auto-generated.
- **Automate it.** Drive it from commit messages (see [`commit-and-pr-hygiene`](../commit-and-pr-hygiene/SKILL.md) — Conventional Commits and `type: description` conventions make this trivial) or from issue-tracker labels. Tools: `git-cliff`, `standard-version`, `semantic-release`, `release-please`, GitHub's autogenerated release notes.
- **Keep the format stable.** [Keep a Changelog](https://keepachangelog.com) is a widely-used convention.

### Release notes

- **Audience:** users.
- **Content:** what's new, what's changed, what to watch out for (breaking changes, migration steps, deprecations).
- **Level of detail:** curated. A hundred bugfixes become "we fixed a number of stability issues in the export path." A three-line feature becomes a paragraph with a screenshot.
- **Voice:** written for the user, not the shipper. *"You can now export as PDF"* beats *"Added `PdfExporter` class to `com.acme.export`."*
- **Human-authored.** The changelog is the raw material; the release notes are the edited version.

If forced to pick one to start, release notes — users are the ones who suffer from the absence.

## Callout — Release repository vs. version control

Version control is for source. A release repository is for artifacts. They serve different consumers, at different scales, with different retention needs.

**What a package repository gives you that VCS doesn't:**

- **Artifact-shaped storage.** Versioned binaries, checksums, GPG signatures, metadata (dependencies, license, size) exposed via a standard API that package managers already speak.
- **Deployment integration.** Deploy tools (Ansible, Terraform, ArgoCD, `helm`, `kubectl`, ECS/EKS pipelines) can pull directly.
- **Search and query.** *"What's the latest 2.x version?"* is one API call, not a Git history walk.
- **Retention and quotas.** Keep the last N versions of each release stream, expire old snapshots, protect production tags.
- **Isolation.** Developer traffic (clone, fetch) doesn't compete with deploy traffic (pull the same artifact from a thousand nodes at once).

**Options:**

- **Language-specific public registries** — PyPI, npm, crates.io, Maven Central, RubyGems, Packagist. Right for open-source libraries.
- **Hosted general-purpose registries** — Artifactory, Nexus, Cloudsmith. Right for organizations shipping many kinds of artifacts.
- **Cloud-provider or platform registries** — GitHub Packages, GitLab Package Registry, AWS ECR, Google Artifact Registry, Azure Container Registry. Right when you're already deeply on the platform.
- **Container registries** — Docker Hub, ghcr.io, ECR, Harbor. Right for container images specifically.

If a team is publishing to Git tags and calling it a release, the migration to a real registry is often smaller than they expect and pays back on the first bad day.

## Output style

Follow the [Output Protocol](../../../../docs/METHODOLOGY.md#10-output-protocol).

- **One question per turn.** Don't fire the Step 2 menu as a wall of questions.
- **Work on their actual release.** If they share a changelog draft, release notes draft, or CI publish config, walk through *theirs*, not a generic template.
- **Name the specific tooling.** `git-cliff`, `semantic-release`, `cargo publish`, `twine upload`, `npm publish`, `mvn deploy`, `gh release create`, `helm push` — call out what they'll actually type.
- **Don't force process on a solo project.** A one-person library on GitHub doesn't need a release train; it needs a stable tagging habit and a changelog. Calibrate.
- **When they've already shipped a broken version**, help them recover (yank + fix-version + honest release notes) — don't lecture them about immutability first.

## When NOT to use this skill

- The user is designing the build that produces the package. Route to [`build-and-package`](../build-and-package/SKILL.md).
- The user is choosing between libraries, resolving version conflicts, or asking about SemVer semantics themselves. Route to [`dependency-management`](../dependency-management/SKILL.md).
- The user has a published release and is now deploying it into environments, or gradually rolling it out with flags/canaries/blue-green. Route to [`operator-playbook`](../operator-playbook/SKILL.md); a dedicated rollout skill is planned.
- The user is asking how to write a good commit message or PR description. Route to [`commit-and-pr-hygiene`](../commit-and-pr-hygiene/SKILL.md).
- There's an active production incident triggered by a bad release. Route to [`incident-response`](../incident-response/SKILL.md); roll back first, tighten the release process later.
- The user is doing greenfield project planning and hasn't yet built anything to release. Skip until they do.
